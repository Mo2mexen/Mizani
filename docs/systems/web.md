# Web page (every role's screen)

The page everyone signs in to. A triage nurse enters a patient, watches the agent work, reads the proposal with the rule behind every number, approves or overrides it under their own account, and keeps an eye on the waiting room. A doctor sees the waiting room in priority order and the handovers nurses released. An admin manages the accounts. The page only shows what the API sends; it never computes, changes or reorders a colour.

## Where it lives
- Code: `web/` (React 19, Vite, TypeScript); all API calls in `web/src/api.ts`, shapes in `web/src/types.ts`; the shell and the role's screens in `web/src/App.tsx`, the session (who is signed in, the idle sign-out) in `web/src/session.ts`
- Served by: the API at `/` from `web/dist` (`MIZANI_WEB_DIR`); the Dockerfile builds it in a Node 22 stage, so `docker compose up` serves it at `http://127.0.0.1:8090`
- Tests: `npm run build` (type check and build, also in CI); `tests/test_api.py` checks the API serves the page and still answers under `/api`
- Settings: `VITE_USE_MOCK=true` in `web/.env.local` answers every call from `web/src/mock/` (fake values, marked as such). Sign in with any password; the user name picks the role: `doctor…`, `chief…` (a doctor with the chief flag), `admin…`, anything else a nurse, and `new…` asks for a new password first

## How it works
**Signing in.** The page opens on a sign-in screen (user name, password). A one-time password leads straight to "Choose your own password" (typed twice, at least 10 characters), and the one-time password is not asked again. After 15 minutes without a key press, click or touch the page signs out by itself and says why; "Switch user" in the header signs out in one click for the next person on a shared tablet; the Account menu has Change password (a dialog: current, new, again) and Sign out. A 401 from any request (the session ended elsewhere, or an admin signed the person out) brings the sign-in screen back with a line saying so. The open patient stays in the address (`#run=`), so a nurse signed out mid-patient gets the patient back after signing in. The header shows the person's name and role at the right; a role with more than one screen gets tabs. The page's polling sends `X-Mizani-Background: 1`, so it never keeps an idle session alive; every change sends `X-Mizani: 1`.

**The nurse's screen.** The numbers are the nurse's steps: 1 intake and 2 proposal side by side (the proposal is the widest column), 3 the waiting room below. The agent's own steps ("How Mizani got there") come after the waiting room, in a section the nurse can hide; the choice is kept in this browser, and while the agent works the proposal panel says which step it is on. On a phone everything stacks in the same order. "Next patient" empties the intake and puts the cursor in the patient label; the entry stays on screen until then. Several re-measure flags show as one line naming every field to measure. The Details button on a card shows what was recorded, read-only from `GET /api/queue/{triage_id}`: the complaint, the measured vitals and those not measured, the TEWS total, the chart signs with the patient's words, and the decision (approved, or overridden with the reason, by whom, when). A search box over the waiting room filters cards by patient label (it hides, never reorders); a long colour column scrolls on its own, so no patient is ever on a second page. The audit drawer draws the newest 100 calls, with "Show 100 more". Times are 12-hour everywhere ("3:13:48 PM"). Patient label and complaint are marked required; the vitals hint says they are optional. While the agent works, a green breathing dot (still when the system asks for reduced motion) and the current step show it is alive. Fields in the vitals grid share rows (CSS subgrid), so labels, inputs and notes line up whatever wraps. The page uses system fonts only, so it works offline. The logo (a drawn balance scale, `web/public/favicon.svg`; *mizani* means scale) is the browser tab icon and sits before the name in the header. A white "?" next to Shadow mode explains it on hover or keyboard focus (you choose first; for training, or to see how often you and Mizani agree). A card's Details, Re-check and Handover buttons stay pressed while their panel is open; the handover panel's button is "Draft handover with AI". Look and behaviour follow docs/DESIGN.md.
1. **Intake.** Patient label, complaint (free text, `dir="auto"` for Arabic) and the vitals. Every vital is optional; an empty one means "not measured" and the backend asks for a re-measure. SpO₂ is labelled as not scored. Submit (or Enter) calls `POST /api/intake` and gets a run id; the button waits until the API has answered once.
2. **Proposal.** While the agent works, the panel shows how long it has taken, and after 20 s that the model may still be loading (the first patient after a start can take a minute or two). Then: the colour, big, with its name, label and the sourced reason. The plain line above the rule ("Set by the chart sign …" or "Set by the vital signs: TEWS n") is read from the engine's cited reason, so the two never disagree: a sign that only gives the same colour as the TEWS did not set it; a red "nurse to confirm" box when a red colour rests on the complaint alone (`confirm_sign`), and until the nurse ticks that she checked the sign the colour itself reads as unconfirmed: a dashed, hatched band, the words "if confirmed" next to the colour name, and a line saying what the vitals alone score (added after a doctor's answer, docs/interview/answers.pdf, answer 10); the complaint; the TEWS table (each vital, its points and the rule); the chart signs, each with the complaint's words behind it (`quote`) and its source; and the flags, each with its source. Shadow mode first asks the nurse for their own colour (`POST /api/triage/{run_id}/assessment`) and only then shows Mizani's; until then the trace hides every step's input and output too. A dropped connection shows "lost the connection; retrying" and the stream resumes on its own; a run the API lost in a restart says so, and the nurse starts the intake again. When the model gave no chart signs (it did not answer), a box under the colour says the chart signs were not checked and that the complaint must be checked against the chart by hand.
3. **Decision.** The decision is saved under the signed-in nurse's name (the panel says so: "Saved under your name, Amina Otieno"); there is no name field. With a "nurse to confirm" box, Approve also needs the nurse to tick that they checked the sign with the patient; Override does not. An override needs a colour (from `/api/colours`) and a reason. "Enter re-measured vitals" highlights the fields the backend flagged and sends `POST /api/triage/{run_id}/vitals`; a new proposal follows on the same stream. Approve and override send the proposal's `triage_id`, so a decision made on a proposal that was re-scored in the meantime is refused ("the proposal changed"). Any refusal is shown with the server's reason. After saving, the panel shows who saved which colour and whether the FHIR record was written.
4. **Agent trace.** An `EventSource` on `/api/triage/{run_id}/stream` lists every model call and tool call as it happens: time, kind, name, latency, the tokens a model call read and wrote (`1,985 in · 146 out` (the roof fall, measured on 16 Nov)), and one readable line each for the input and the output (the signs and quotes the model asked for, the TEWS points, the signs the server applied or refused, the proposed colour and its reason, the commit and the FHIR ids). The title line adds up the run: model calls, tokens in and out, tool calls, seconds. Click a row for the raw JSON. With the second look on, a `review` step shows the model's final list of signs; a model call that failed is shown as "the model did not answer".
5. **Waiting room.** One column per colour, in the rule pack's order, with the target time and its source; cards in the order the API sends (refreshed every 5 s): time waited, time since the last triage against the target time, and a "re-check due" badge from the re-triage watch. Each card can be re-checked with fresh vitals (`POST /api/queue/{triage_id}/retriage`, which starts a new run shown above; a double click starts one run) and can get a doctor handover: the model drafts it, the nurse reads it and releases it to the doctors' inbox under their own name. **Called in** records, under the nurse's name, that the patient went in to be seen; the card then leaves the waiting room and the record stays.
6. **Audit drawer** (every role). Every logged tool call and account event (sign-ins, refused sign-ins, account changes), newest first (time, tool, approver, model, tokens in, tokens out, latency, cost, refused or not), whether the hash chain is intact, the shadow-mode agreement (for a nurse), and the model's use across the log: the number of agent runs that called it, the average tokens in and out per run, and the total cost. Rows logged before 16 Nov 2026 have only a total, shown when you hover the Tokens in cell. It takes focus when opened; Escape or Close returns focus to the button that opened it.

**The doctor's screen** (`DoctorView.tsx`). Two panels: the waiting room as one list, most urgent colour first, then the longest wait, each row with the colour as its left edge and its printed name, the time waited against the time to be seen (red when past it) and RE-CHECK DUE; "Details" shows what was recorded, and "Seeing this patient" asks once ("Record that I am seeing them") and takes the patient off the waiting list under the doctor's name. Beside it, "Handovers from nurses": the latest released handover of each waiting patient, newest first, with who released it and when. Both refresh every 5 s. A doctor has no intake, decision or re-check controls.

**Admin › Users** (`AdminUsers.tsx`). A table of every account (name, user name, role with "Chief flag given by X on 16 Nov 2026", status: active, has a one-time password, locked until a time, or deactivated; last sign-in) and, beside it, "Add a person" (full name, user name suggested from it, role with one line on what the role can do). Adding a person or resetting a password shows the one-time password once, in a box with Copy (or the text selected for copying where the browser has no clipboard on plain HTTP) and "Done, I have given it". Manage opens a row with the role, the chief flag for a doctor, Reset password, Sign out everywhere and Deactivate or Reactivate; the last three ask for confirmation in words that name the person and what will happen. An admin cannot change their own role or deactivate themselves. On a phone the table turns into one block per person.

**Admin › Model** (`AdminModel.tsx`, the admin's second tab). "Where the model runs": what is in use now and who chose it, then three choices: This server (the model that came with Mizani), A GPU server in this hospital, A cloud GPU server, each with one line on where complaint text goes. The other two ask for the address, the model name, an API key (a saved key is never shown; leaving the field empty keeps it) and whether to send the thinking setting. A cloud choice shows a red box, "Complaint text will leave this hospital", with a box to tick. "Test connection" shows the measured time or the reason it failed; Save is enabled only after a successful test of the same values (and the tick, for a cloud server), so a wrong address cannot leave the nurses without a model.

Accessibility: every input has a visible label (or a hidden one tied to it), every action is a button or a form reachable by keyboard with a visible focus ring, results are announced through one polite live region, errors use `role="alert"`, text meets WCAG AA contrast, and motion stops under `prefers-reduced-motion`.

## Depends on / used by
- Depends on: the API (api.md) and its event stream; nothing else, no fonts or scripts from the internet.
- Used by: triage nurses at the desk, doctors, the hospital's admin; the demo video (recorded before sign-in existed).

## Safety rules this system enforces
- The page never decides: colours, target times, the colour list and the queue order come from the API; there is no drag and drop.
- Nothing is saved without a signed-in nurse: the name on every decision, handover release and called-in record is the account's, and the server checks the role again. A red colour from the complaint alone also needs the nurse's tick before Approve.
- The page shows each role only its own screens, but the server is what refuses (api.md); a shared tablet signs out after 15 idle minutes, and the API's answers are never cached by the browser.
- Every number shows its source: each TEWS point, chart sign, flag and target time prints the rule or input field it came from, and each sign from the complaint shows the words behind it.
- Patient text is data: the complaint, quotes and the handover are rendered as plain text, never as HTML, with `dir="auto"`.
- No approval token ever reaches the page; the commit step shows it as "(hidden)".
- Colour is never the only cue: every colour is printed with its name.

## Running and testing it alone
```
cd web && npm ci
VITE_USE_MOCK=true npm run dev           # http://localhost:5173 with fake data, no backend
npm run dev                              # same page against the API on 127.0.0.1:8090 (Vite proxies /api)
npm run build                            # type check + build into web/dist; `uv run mizani-api` then serves it at /
```

## Known limitations
- The queue refreshes by polling every 5 s, not by a push stream.
- Handover drafts are only shown for the current session; the record view (`GET /api/queue/{triage_id}`) has the history.
- English interface only; complaints and handovers can be Arabic and display right to left.

## Extending it
A new screen is a component in `web/src/components/` with its calls added to `web/src/api.ts` and `web/src/mock/`. If it needs a new API shape, change the API first and describe it in api.md.
